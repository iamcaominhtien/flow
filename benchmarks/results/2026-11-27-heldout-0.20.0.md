# Held-out evaluation of 0.20.0 (working method) against 0.17.0

Date: 2026-11-27. Plugin versions: 0.17.0 (`aeef609`, `main`) and 0.20.0 (`f2f9d6f`). Briefs, answers and rule: `benchmarks/heldout/`. Harness as it ran, bugs included: `benchmarks/heldout/harness/`. Reviewed by an independent agent before this was written.

## Verdict

**By the rule fixed in advance: 0.20.0 is not better.** And the test was mostly **not a test of the change**: Flow ran in 7 of 28 runs, and in none of the 12 runs on h3, h4 and h5. 0.20.0 is kept, marked as unmeasured; nothing here shows a benefit, and nothing beyond grader noise shows harm.

- Gain rule (briefs with control 3 or less: h3-h6, new must have the higher mean gain on 3 of 4, ties against new): new wins h4 (4.5 vs 4) and, only through the bug, h6; ties on h3 and h5. **Fails.**
- Fidelity (five drawn elements per run judged against the source): wrong or invented, old 2, new 5 (the old run without a graded picture counted as 0). **Fails.** The judged errors on both sides are small (a `--continue`/`--skip` arrow merged, "the tool" for "the admin tool").

## Why the test did not test the change

- **Flow was bypassed.** In 21 of 28 runs the agent wrote its own HTML or SVG and screenshotted it. The requests do not say "use the flow plugin" (the owner's original request did); they ask for a PNG while every skill promises "an animated HTML page and a draw.io file"; they carry a hint that Playwright works; and the skill descriptions key on type names, not on "draw a diagram of this code, data or meeting". This is a plugin gap of its own: a generic request to draw something from an input mostly does not reach the plugin.
- **Where 0.20.0 was loaded (3 runs), its mechanisms ran every time**: each wrote `<name>.brief.md` and used `view.js`. That shows the method reaches an agent that loads a skill, not that it helps.
- **The environment was not the owner's**: the runs inherited this container's harness prompt and twelve other synced plugins, one of which claims all visual output.

## What the grading cannot do at this size

- Near-identical answers were scored 0 in one run and 1 in another (h4 question 4: that single flip is the whole h4 "win"). One flipped item moves a brief's mean by 0.5.
- The fidelity judge picks its own five elements per run, so counts are not comparable across runs, and it is strict in uneven ways.
- Scores sit at 4-5 (ceiling); one question (h3 question 3) was missed by all eight runs.
- The answering model could read the held-out folder, which holds `ANSWERS.md`; whether it did is not logged. Not verified either way.
- `view.js` renders of 0.20.0 were graded as extra pictures.
- The rule was committed about a minute after the first old run finished, before any grading; the tie rule added later goes against the new version.

## Next

1. Fix the grader: find every new PNG in the work folder, give the answering model only the pictures, score each answer three times by majority, and judge fidelity against a fixed list of facts per brief.
2. The bypass first, tested on its own: write 30 or more fresh, varied requests (and some that should not use the plugin) before changing anything, measure how often the plugin is picked, on a held-out half. A likely fix is one broad entry skill (draw a diagram from any input, PNG included) that carries the working method and routes to the type skills.
3. Then a new pre-registered quality test on new briefs, with requests that engage the plugin as the owner's did, without the Playwright hint, and with the plugin-use rate reported.
